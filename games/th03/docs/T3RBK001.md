# T3RBK001 rollback state

Status: implemented for the `Game` simulation owner. The shared Raster/TRAM
section is separately implemented as `T3RBV001`, the private retained MAIN
presenters are covered by `T3RBP001`, and `T3RBM001` now composes them with
process-local semantic audio into one transactional `MainProcess` image. None
of this enables networking yet.

## Purpose and trust boundary

`T3RBK001` is a private, arbitrary-input-boundary image used by the future
local rollback coordinator. It is never a replay file, never loaded from a
peer, and never a server or user-data format. Its job is to restore the same
already-authenticated gameplay configuration after speculative local frames.

The image is field-wise and architecture-neutral. It contains no C++ object
images, pointers, padding, host-sized integers, allocator state, or borrowed
lifetimes. Signed integers and fixed-point representations use their exact
little-endian bit patterns; booleans use one byte; arrays are dense; optionals
use one 0/1 presence byte. The code order in
`src/core/rollback_snapshot.cpp` is the schema authority.

## Fixed in-memory envelope

`RollbackSimulationSnapshot` owns a zero-filled 96 KiB byte array and one
32-bit active length. Capture and restore allocate no heap storage. A future
16-boundary ring therefore reserves exactly 1,572,928 bytes for this simulation
section.

The 32-byte active header is:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 8 | `T3RBK001` |
| 8 | 2 | version 1 |
| 10 | 2 | header size 32 |
| 12 | 4 | active image bytes |
| 16 | 4 | payload bytes |
| 20 | 4 | payload FNV-1a integrity check |
| 24 | 4 | canonical immutable-configuration fingerprint |
| 28 | 4 | section flags; bit 0 means simulation |

The payload includes every `detail::DeterministicState` field plus the mutable
warning-interstitial count, recorded-pause deferred inputs and boundary,
defeat timing latches, live-pause phase/context/boundary, terminal-finish latch,
effective round-reset seed, and retained round-start observation. Immutable
initial configuration, authenticated `GameContent`, and input protocol remain
owned by the live `Game`; their canonical fingerprint prevents cross-owner
restore.

The FNV value detects accidental local corruption. It is not the future peer
desync digest and is not a security boundary. Phase N0 still owes SHA-256 over
the authoritative simulation bytes at the application/netplay layer.

## Frozen vector and measurements

The cross-compiler core fixture after 48 deterministic VS frames is exactly
70,353 active bytes with whole-image FNV-1a `3718020633`. GCC and MSVC both
produce that vector and byte-identical restore/resimulation output.

On the development Ryzen host, a 2,000-iteration optimized GCC microbenchmark
measured approximately:

- capture: 0.414 ms;
- restore: 0.444 ms;
- one synthetic core frame: 0.0012 ms.

These are engineering measurements, not minimum-machine acceptance results.
Even capture plus restore is comfortably below one 17.723 ms source deadline
on this host.
